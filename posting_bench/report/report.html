posting_bench · experiment report

Intersecting and merging compressed posting lists

I implemented 13 posting-list representations and 20 intersection and union algorithms in Rust, built a testbed that checks every query result before it is timed, and ran them on synthetic and real collections. This page explains each technique with its formulas and layout, then reports what was measured.

The problem

An inverted index maps every term \(t\) to its posting list \(\mathcal{L}_t\): the strictly increasing docIDs of the documents that contain it, drawn from a universe of \(u\) documents. A query \(q = \{t_1, \dots, t_k\}\) is answered with set operations over the lists:

\[ \mathrm{AND}(q) = \bigcap_{i=1}^{k} \mathcal{L}_{t_i}, \qquad \mathrm{OR}(q) = \bigcup_{i=1}^{k} \mathcal{L}_{t_i}, \qquad \mathcal{L}_t \subseteq [0, u),\ n_t = |\mathcal{L}_t| . \]

Lists are stored compressed, so the representation decides both the index size and how cheaply a list can be scanned (next) or skipped through (NextGEQ(x), the first posting \(\ge x\)). For two lists with \(m \le n\) postings, any comparison-based intersection must distinguish all interleavings of the two lists, which gives the lower bound

\[ \log_2 \binom{n+m}{m} \;=\; m \log_2 \frac{n}{m} + O(m) \ \text{comparisons}, \]

so when the lists differ a lot in size, a good algorithm touches only a small part of the longer list. Union is different: its output alone has up to \(N = \sum_i n_i\) elements, so the work is dominated by sequential decoding and by how cheaply the results can be merged.

The two figures of merit used throughout are space and query time:

\[ \text{bits/posting} = \frac{\sum_t \lvert \mathrm{enc}(\mathcal{L}_t) \rvert}{\sum_t n_t}, \qquad \text{ms/query} = \min_{r \in \text{reps}} \frac{T_r}{|Q|} . \]

\(\lvert \mathrm{enc}(\cdot) \rvert\) counts payload plus every skip pointer, directory and header needed at query time, which is what a serialized index would occupy. \(T_r\) is the wall-clock time of repetition \(r\) over the whole query log \(Q\).

The testbed

The crate is organised around three traits. Every representation implements PostingList (build, size, decode). Representations that can be iterated with skipping implement CursorList, whose cursor exposes docid(), next() and next_geq(x). Representations with their own multi-list algorithms (Roaring, tries, the hybrid index) also implement SetOps. The harness runs every applicable algorithm on every representation, so each codec is measured both through the generic cursor interface and through its native operations.

Representations

The 13 representations fall into four families. All lists in a query share one universe, and every docID is below \(2^{32}-1\), which the cursors use as the end-of-list sentinel.

Gap coding in blocks: VByte, BP128, OptPFor, interpolative

Block codecs cut a list into blocks of 128 postings. Within a block they code d-gaps, which are small when docIDs are dense, relative to a base \(b\) (the previous block's last docID plus one):

\[ g_0 = d_0 - b, \qquad g_i = d_i - d_{i-1} - 1 \quad (1 \le i < 128). \]

A skip table stores each block's last docID and byte offset, 64 bits per block, the same as PISA's block_posting_list. NextGEQ gallops over the skip table, decodes one block and binary-searches inside it.

VByte
7 data bits per byte with a continuation flag: \(8 \lceil w(g)/7 \rceil\) bits per gap, where \(w(g) = \lfloor \log_2 g \rfloor + 1\) is the bit width. Byte-aligned and branchy.
BP128
Frame of reference: one width \(b = w(\max_i g_i)\) per block, so a block costs \(8 + 128\,b\) bits. Values are packed in SIMD-BP128's vertical 4-lane layout so that unpacking is the same shift and mask on 4 lanes. The code is written lane-wise with a compile-time \(b\), and LLVM vectorises it.
OptPFor
Patched frame of reference. Gaps wider than \(b\) bits become exceptions, stored as a position byte plus their high part in VByte, and \(b\) is chosen per block to minimise \[ \mathrm{cost}(b) = 16 + 128\,b + \sum_{g_i \ge 2^b} \Bigl(8 + 8 \Bigl\lceil \tfrac{w(g_i) - b}{7} \Bigr\rceil\Bigr) \ \text{bits}. \]
Interpolative
Binary interpolative coding (Moffat & Stuiver). The middle element \(d_m\) of a range \([\ell, r]\) holding \(n\) values is coded in the range it can actually occupy, then both halves recurse: \[ d_m \in [\,\ell + m,\ r - (n - 1 - m)\,] \;\Rightarrow\; \lceil \log_2 (r - \ell - n + 2) \rceil \ \text{bits}. \] A run of consecutive docIDs costs zero bits.

Elias-Fano and partitioned Elias-Fano

Elias-Fano splits each value into \(\ell\) low bits, stored verbatim, and a high part, stored in unary in a bitvector. Element \(i\) with high part \(h_i\) sets bit \(h_i + i\):

\[ \ell = \Bigl\lfloor \log_2 \frac{u}{n} \Bigr\rfloor, \qquad \text{bits} = \underbrace{n\,\ell}_{\text{low}} + \underbrace{n + \lfloor u / 2^{\ell} \rfloor + 1}_{\text{high}} \;\le\; n \Bigl( 2 + \Bigl\lceil \log_2 \frac{u}{n} \Bigr\rceil \Bigr). \]

Bucket \(h\) of the high bits starts right after the \(h\)-th zero, so NextGEQ(x) jumps to \(\mathrm{select}_0(\lfloor x / 2^{\ell} \rfloor - 1) + 1\) without decoding anything before it. The implementation samples every 256th zero to answer \(\mathrm{select}_0\) in constant time, and scans instead when the target is within a few buckets, as PISA does.

Plain Elias-Fano ignores clustering: its size depends only on \(u\) and \(n\). Partitioned Elias-Fano (Ottaviano & Venturini) cuts the list into partitions and codes each one relative to its own base with the cheapest of three encodings: a full run (no payload), a bitvector over the partition's range, or Elias-Fano over that range. The partitions are chosen by dynamic programming over boundaries every 32 postings:

\[ C(j) = \min_{\substack{i < j \\ j - i \le 4096}} \Bigl[\, C(i) + 64 + \min\bigl\{ \mathrm{EF}(i, j),\ \underbrace{d_{j-1} - d_{i-1}}_{\text{bitvector}},\ \underbrace{0}_{\text{if a run}} \bigr\} \Bigr], \]

where 64 bits pays for the partition's entry in the upper level (last docID and descriptor), the fixed cost PISA uses.

Roaring bitmaps

Roaring partitions the universe rather than the list. The high 16 bits of a docID select a chunk; the low 16 bits go into that chunk's container, whichever of three is smallest:

\[ \text{array: } 16\,c \ \text{bits}, \qquad \text{bitmap: } 2^{16} \ \text{bits}, \qquad \text{run: } 16 + 32\,r \ \text{bits}, \]

for \(c\) values in \(r\) runs; arrays switch to bitmaps at \(c = 4096\), where \(16c = 2^{16}\). Because every list uses the same chunk boundaries, AND and OR proceed chunk by chunk with container-pair kernels and need no NextGEQ per element:

  • array ∩ array: SSE4.2 pcmpistrm all-pairs compare (CRoaring's intersect_vector16), or galloping when one side is more than 64× larger;
  • bitmap ∩ bitmap: word AND with popcount;
  • array ∩ bitmap: bit probes;
  • union: a k-way merge over keys that ORs dense chunks into one bitmap and counts it once at the end.

Compact binary tries

Arroyuelo & Castillo (CPM 2023) store a set as the binary trie of height \(h = \lceil \log_2 u \rceil\) that spells every docID most significant bit first. Each node contributes two bits, "left child present" and "right child present", and the bits of a level form a bitvector \(B_\ell\) with rank support. Children are found by counting ones:

\[ \mathrm{left}(i) = \mathrm{rank}_1(B_\ell, 2i), \qquad \mathrm{right}(i) = \mathrm{rank}_1(B_\ell, 2i + 1). \]

Intersection walks all \(k\) tries in lockstep and ANDs the 2-bit codes at each node, so a subtree missing from any input is pruned immediately. This runs in \(O(k\,\delta \log(u/\delta))\) time, where \(\delta\) is the alternation: the size of the smallest certificate that proves the result. DocIDs that are close share their upper paths, so clustered lists need few nodes. The run-compressed variant (Run-Trie) cuts every full subtree and codes its root as 00.

Hybrid bitmap + list index

Culpepper & Moffat's hybrid stores a list as a plain bitmap of \(u\) bits when it is dense, \(u / n \le 8\) (at most 8 bits per posting), and as BP128 otherwise. Conjunctions intersect only the sparse lists, rarest first, and then filter every candidate with \(O(1)\) bit probes. Lucene 10.2 uses the same idea per block, storing dense blocks as bitsets.

Algorithms

Two sorted arrays

merge
Two pointers, \(m + n\) comparisons. The branch-free variant derives both pointer increments from the comparison result.
binary search
Search each element of the short list in the rest of the long list: \(m \log_2 n\).
galloping
Exponential search from the last position, probing 1, 2, 4, … steps ahead, then a binary search: at most \(2 \sum_i \log_2(g_i + 1) \le 2m \log_2(n/m + 1)\) comparisons, which matches the lower bound up to a constant.
Baeza-Yates
Binary-search the median of the short list in the long list, then recurse on both sides: \(O(m \log(n/m))\) on average.
SIMD block merge
Compare a block of \(W\) values from each list all-against-all with \(W\) vector compares against rotations of one block, compact the matches, and advance the block with the smaller maximum. Kernels for SSE (\(W = 4\)), AVX2 (\(W = 8\)) and AVX-512 (\(W = 16\), which emulates VP2INTERSECT).
adaptive
SIMD block merge when \(n/m \le 64\), galloping beyond, which is CRoaring's switch point.

k lists

SvS
Set versus set: sort by length and intersect the two shortest lists, then intersect the running result with each next list. Barbay et al. and Culpepper & Moffat found it the fastest in practice.
Small Adaptive
Demaine, López-Ortiz & Munro: take the next element of the currently shortest list and gallop for it in the others, re-sorting by remaining length.
Sequential
Barbay & Kenyon's round-robin eliminator, optimal for the alternation measure: \(\Theta\bigl(\delta \sum_i \log (n_i / \delta)\bigr)\) comparisons.
leapfrog
The cursor form of SvS used by PISA and Lucene: the rarest list proposes a candidate and every other cursor calls NextGEQ. A miss makes the larger docID the new candidate.
round-robin
Leapfrog Triejoin's unary case: cursors take turns seeking to the current maximum.
decode + SvS
Decode every list completely, then intersect the arrays (Lemire et al.).

Union

heap
k-way merge with a binary heap of cursors: \(O(N \log k)\).
min-scan
Scan all cursors for the minimum at every step (PISA's or_query): \(O(N k)\), but branch-friendly for small \(k\).
bitset window
Lucene's BooleanScorer: drain every cursor into a 4096-docID bitset, then scan the window's 64 words.
fold, bitmap
On uncompressed arrays: pairwise merges smallest first, or set bits in a bitmap spanning \([\min, \max]\) and scan it.

Experimental setup

The clustered collection mimics an index whose docIDs were reordered by URL or topic, the setting where modern indexes operate. The docID space is split into 1000 topic regions; each term draws 85% of its postings from a few preferred regions, in runs of about 4 consecutive documents, and the rest uniformly. The uniform collection uses the same list lengths with random docIDs, like an index in crawl order. WikiText-103 is real text: every paragraph of the training split is a document, in corpus order, so the paragraphs of one article are adjacent.

List lengths follow Zipf's law (\(n_r \approx n_1 / r\)). Queries take 2 to 4 terms that co-occur in a randomly sampled document, so conjunctions are rarely empty, as for real queries. Every measurement is the best of 3 timed passes over the whole query log, single-threaded, after a verified warm-up pass.

Reproduce

Everything is in posting_bench/. The default build uses -C target-cpu=native; every SIMD path has a portable fallback.

cd posting_bench
cargo test --release                      # 56 tests, every codec and algorithm
scripts/prepare_wikitext.sh data          # optional: WikiText-103 (needs pyarrow)
scripts/run_experiments.sh data/wikitext103.txt
python3 scripts/build_report.py           # rebuilds this page from results/*.json

# your own data: ds2i/PISA .docs collections or one document per line
target/release/posting-bench run --source ds2i --input gov2.docs --queries q.txt --json out.json
target/release/posting-bench run --source text --input docs.txt --codecs "pef,roaring,bp128"
target/release/posting-bench kernels --small 10000 --ratios 1,4,16,64,256,1024
