Strata: full text, structured filters and vectors in one SQL file

An embedded search database in the spirit of SQLite: one file, ACID transactions, SQL. Every table is indexed three ways at once (posting lists, a columnar forward index and vector ANN indexes), and a cost-based planner combines them in a single query. This page is the design, the prototype built from the earlier posting-list research, and its evaluation against SQLite and Tantivy on four BEIR collections.

What it does

One file, one SQL statement, three kinds of index: the planner decides per segment which index drives the query and how the others constrain it.

SQLite answers full-text queries with FTS5 and structured ones with B-trees, but it has no vector index, and its FTS5 scores every match without pruning. Search libraries such as Tantivy rank text quickly but have no SQL, no vectors and no transactions. Vector databases do the opposite. Strata keeps SQLite's packaging (an embedded library, one file, a write-ahead log, snapshot isolation) and puts a search engine inside it.

-- full text, ranked, with structured filters
SELECT id, title, score() FROM docs
WHERE MATCH(body, 'vaccine AND (mrna OR "messenger rna") -animal')
  AND year BETWEEN 2019 AND 2021 AND category IN ('c01', 'c02')
ORDER BY bm25(body, 'mrna vaccine efficacy') DESC LIMIT 10;

-- filtered vector search
SELECT id FROM docs WHERE rating >= 4 ORDER BY similarity(emb, :q) DESC LIMIT 10;

-- hybrid ranking: rank fusion, or a weighted sum of normalised scores
SELECT id FROM docs WHERE year >= 2015
ORDER BY 0.2 * bm25(body, :text) + 0.8 * similarity(emb, :q) DESC LIMIT 10;

-- facets over any result
SELECT category, COUNT(*) FROM docs WHERE MATCH(body, 'vaccine')
GROUP BY category ORDER BY 2 DESC LIMIT 5;

The dialect is plain SQL parsed by sqlparser. Search functions are MATCH (boolean full text with phrases, prefixes and negation, juxtaposition meaning AND as in FTS5), bm25, similarity and distance, and rrf, with named options such as nprobe => 32 or strategy => 'prefilter'. Text fields can be generated from other fields, like SQLite's GENERATED ALWAYS AS, so the searchable body (title and text) is indexed without being stored twice.

Architecture

Strata is layered like SQLite, with a search engine where SQLite keeps its B-tree module. SQL text is parsed and bound to the table's schema, giving a predicate tree (text matches, ranges, IN lists under AND, OR and NOT) and a score expression (BM25, similarity, fusion or a column). The planner decides per segment, from statistics the indexes answer without scanning, how each part is evaluated. Operators run on zero-copy views of the segment's sections, mapped straight from the file.

Storage

SQLite updates B-tree pages in place. Compressed posting lists, bit-packed columns and ANN graphs do not survive in-place updates: the best encodings, such as partitioned Elias-Fano, are chosen per list, and changing one docID means re-encoding the list. SQLite's own FTS5, Lucene and Tantivy all keep their indexes as immutable segments merged in the background. Strata does the same for the whole table and adds SQLite's transactional envelope.

Commit and recovery

The commit protocol is shadow paging, as in LMDB: nothing reachable from a valid meta slot is ever overwritten, so there is no rollback journal.

\[ \text{commit}_{t+1}:\ \text{write extents} \;\to\; \text{fsync} \;\to\; \text{write slot } (t+1) \bmod 2 \;\to\; \text{fsync}, \qquad \text{recover} = \operatorname*{arg\,max}_{s \in \{A, B\},\ \text{crc}(s)\ \text{ok}} \text{txn}(s). \]

A torn slot fails its checksum and recovery falls back to the other one, which still names a complete version. Freed pages wait until no snapshot needs them, plus one extra commit, so the older slot always stays valid. A crash test kills a writer process with SIGKILL at random moments, over and over; after every restart the database equals some committed prefix of the writes.

Writes, snapshots and merges

  • Write-ahead log. Inserts and deletes append checksummed records to a -wal file, synced at commit. On open, committed transactions are replayed and a torn tail is ignored.
  • Memtable. Committed but unflushed documents are searchable at once. A snapshot builds small in-memory segments from them with the same code as on-disk segments, one per 1,024 documents, so a write rebuilds only the last chunk.
  • Snapshots. A snapshot is a reference-counted manifest version. Readers never wait for the writer, and a held snapshot keeps its pages from reuse.
  • Deletes and updates. Each segment has a primary-key index and a delete set, replaced copy-on-write. An update is a delete plus an insert.
  • Merges. A tiered policy merges segments of similar size. It reads the live documents back (stored fields from the doc store, vectors from their sections, generated columns recomputed) and rebuilds every index, which drops deleted documents and re-optimises encodings for the larger lists. vacuum compacts the file.

Indexes

Every field type maps to the structures that serve it. The posting-list study that preceded this design chose the encodings: Loom for ranked text, Pyramid for filter lists, BP128 for short lists.

Full text

The analyzer splits on non-alphanumeric characters, lowercases, folds accents, drops 33 stopwords and applies the Snowball English stemmer. Ranked queries also drop NLTK's 153 English function words and count each term once. Terms sit in front-coded dictionary blocks of 32. Lists of at least 512 documents keep their docIDs as Loom, with frequencies bit-packed per 128 postings and addressed by posting rank; shorter lists use BP128 blocks. Document lengths are one-byte norms. Ranking is BM25 with collection-wide statistics summed over the snapshot's segments, so a document scores the same in any segment:

\[ \mathrm{BM25}(d, q) = \sum_{t \in q} \ln\Bigl(1 + \frac{N - n_t + 0.5}{n_t + 0.5}\Bigr) \cdot \frac{f_{t,d}\,(k_1 + 1)}{f_{t,d} + k_1\bigl(1 - b + b\,\frac{|d|}{\overline{|d|}}\bigr)}, \qquad k_1 = 1.2,\ b = 0.75. \]

Top-k uses MaxScore by default: terms are sorted by their upper bound \(U_t\), and once the threshold \(\theta\) of the current top-k exceeds the sum of the smaller bounds, those lists stop driving iteration and are only probed. Block-Max WAND is available, but on these natural-language queries (often 8–15 terms) MaxScore measured 2–2.5× faster. A filter either drives scoring, when it is small enough that scoring its members directly is cheaper, or is probed per candidate. The crossover is a fitted constant times the filter size against the query's list lengths.

Structured fields

  • Columns. Integers and floats sit in 128-document blocks, frame-of-reference bit-packed, with min/max zone maps per block and per 4,096-document superblock. Two-decimal floats such as rating are detected and stored as scaled integers (0–499).
  • Keyword postings. Each value has a Pyramid docID list (a sorted array below 64 documents), so equality and IN are unions. Per-candidate probes instead use the code column and a bitset of accepted codes, at 6–9 ns against 9–24 ns for Pyramid probes.
  • Range postings. An equi-depth histogram of 64 buckets stores each bucket as a Pyramid list. A range is the union of the buckets it covers plus the two boundary buckets checked against the column. Counting is exact from the histogram for whole buckets. The histogram is also the planner's selectivity estimator.
  • Facets count either by reading the result's codes, or by count-only Pyramid intersections when the result is large and the values few.
  • Doc store. Rows are kept in LZ4-compressed 16 KiB blocks.

Vectors

Each vector field keeps float32 vectors for exact re-ranking and 8-bit codes for scanning. Codes are per-dimension scalar quantised, and the query is quantised too, so the inner loop is an integer dot product on AVX-512 VNNI:

\[ c_i = \Bigl\lfloor \frac{x_i - \min_i}{\Delta_i} \Bigr\rceil, \qquad \langle q, \hat{x} \rangle = \sum_i q_i (\min_i + \Delta_i c_i) \;\approx\; \alpha \sum_i \tilde{q}_i\, c_i + \beta, \]

with \(\tilde q\) the 8-bit query, \(\alpha, \beta\) per-query constants, and one 1,024-dimension score in 10–15 ns. Three index kinds sit on top. Flat scans codes and re-ranks the best \(r\) in float32. IVF stores each k-means cluster's docIDs contiguously, followed by their codes, so a probe is one sequential read and a filter is an intersection with the cluster's docID list. HNSW keeps fixed-degree adjacency arrays in the segment; filtered HNSW traverses through non-matching nodes but only collects matching ones.

Planner

The planner works per segment from statistics the indexes answer in microseconds: exact list lengths for terms and keyword values, histogram counts for ranges, document counts, and the vector index's calibrated cost model. Conjunctions assume independence and disjunctions use inclusion-exclusion:

\[ \hat s(P_1 \wedge P_2) = \hat s(P_1)\,\hat s(P_2), \qquad \hat s(P_1 \vee P_2) = 1 - (1 - \hat s(P_1))(1 - \hat s(P_2)), \qquad \hat s(\neg P) = 1 - \hat s(P). \]

Materialise or probe

A predicate is either evaluated into a document set before ranking, or checked per candidate of the ranking operator. If that operator tests \(m\) candidates, it materialises when

\[ C_{\text{mat}}(P) < m \cdot c_{\text{probe}}(P), \qquad c_{\text{probe}}(P_1 \wedge \dots \wedge P_k) = \sum_{i=1}^{k} c_i \prod_{j < i} \hat s_j \quad (\hat s_1 \le \hat s_2 \le \dots), \]

so a conjunction is probed most selective leaf first, short-circuiting. Inside a materialised conjunction the same test applies child by child: once the running result is small, each remaining child is probed per survivor instead of materialised.

Filtered vector search

Four strategies compete. Pre-filter scans the filter's members exactly. In-index searches IVF or HNSW with the filter applied inside. Post-filter searches unfiltered with \(k' \approx k/s\) and drops non-members. Flat scans everything. Their costs, from the vector index's model, are roughly

\[ C_{\text{pre}} \approx C_{\text{mat}} + s\,n\,c_{\text{sq8}}, \qquad C_{\text{HNSW}} \approx \frac{\text{ef}\cdot M\,c_{\text{dist}}}{s_{\text{near}}}, \qquad C_{\text{IVF}} \approx \frac{\text{nprobe}}{\sqrt{s_{\text{near}}}}\cdot\frac{n}{n_{\text{list}}}\,c_{\text{sq8}}, \qquad C_{\text{post}} \approx C_{\text{index}}\Bigl(\frac{k}{\min(s, s_{\text{near}})}\Bigr). \]

The index strategies pay for the selectivity near the query, \(s_{\text{near}}\), not the global \(s\). A filter on a topic far from the query has almost no members among the query's neighbours, so HNSW wanders through thousands of nodes. When the global estimate favours an index strategy, the planner measures \(s_{\text{near}}\) with a 32-result unfiltered search and re-plans:

\[ \hat s_{\text{near}} = \frac{\bigl|\{\, d \in \mathrm{NN}_{32}(q) : P(d) \,\}\bigr| + \tfrac12}{32 + 1}. \]

Hybrid ranking

Reciprocal rank fusion and weighted fusion are both one SQL expression:

\[ \mathrm{RRF}(d) = \sum_{i} \frac{1}{60 + \mathrm{rank}_i(d)}, \qquad \mathrm{W}(d) = \sum_i w_i\, \frac{s_i(d) - \min_{C} s_i}{\max_{C} s_i - \min_{C} s_i}, \]

where \(C\) is the union of each input's top 100. With exact => 1, \(C\) is every row passing the filter, which gives the reference ranking for measuring how much the top-100 shortcut loses.

Evaluation

Four BEIR collections, with Cohere embed-english-v3 vectors (1,024 dimensions) for documents and queries, and human relevance judgments: SciFact (5,183 documents), FiQA (57,638), TREC-COVID (171,332) and Quora (522,931). Each document also has synthetic structured fields: year uniform over 1990–2024, category Zipf-distributed over 64 values, rating uniform over [0, 5). A content-correlated topic (the k-means cluster of the document's vector) gives filters that correlate with queries. One generated workload per collection is run by all three systems: BM25, boolean, filter, vector, hybrid and facet queries, at filter selectivities from 0.1% to 50%.

Each system is fully built (one Strata segment, one Tantivy segment after merging, one SQLite file), then measured single-threaded on a 4-core Xeon with AVX-512, nothing else running. Warm latency is the median of up to three repetitions per query. Cold runs close the database, evict its files from the OS page cache, reopen and run one query; pages read are the file pages the query brought into the page cache.
